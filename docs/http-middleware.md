# HTTP middleware product boundary

AsterGate uses the official Forge Axum adapters for CSRF, runtime CORS, direct-peer/trusted-proxy IP resolution and process-local governors. It does not enable Actix or use a sibling workspace patch. Gate owns route selection, trusted deployment settings, Cookie lifecycle and typed error responses.

## Cookie-authenticated API writes

Every unsafe Account/setup/management request needs exactly one X-AsterGate-Request: 1, exactly one X-AsterGate-CSRF header and exactly one matching readable CSRF cookie. The token is 32–128 URL-safe ASCII bytes. Repeated Cookie token values, token headers, Host, Origin, Referer and Sec-Fetch-Site are rejected. Forge performs token comparison and request-source checks. GET/HEAD/OPTIONS do not require tokens.

GET /api/v1/setup/status and /api/v1/public/frontend-config bootstrap the CSRF cookie if it is absent. Existing valid cookies are retained, avoiding bootstrap-induced rotation. HTTP loopback uses ag_csrf; HTTPS uses __Host-ag_csrf. Both are host-only, Path=/, SameSite=Strict, readable by the same-origin frontend; HTTPS adds Secure. Session cookies remain HttpOnly and SameSite=Lax. Setup/login routes explicitly issue session and CSRF cookies together after the session transaction commits. Logout, current-session/revoke-all, password/email change and Account deletion explicitly clear both cookies after successful revocation; revoking another session leaves both cookies untouched. Middleware never infers this lifecycle by parsing Set-Cookie output. Handler failures never rotate a cookie. A damaged authentication configuration does not cause public status/branding reads to mint cookies from a fallback policy.

The frontend reads its host's token for each mutation. If absent it coalesces concurrent bootstrap calls. It never attaches the token to another origin or a non-API path, never stores the token in localStorage, and never automatically retries a mutation. CLI clients must first retain the bootstrap cookie and then echo it in the two required headers. For example, use a cookie jar with GET setup/status; supply X-AsterGate-Request: 1 and X-AsterGate-CSRF equal to that jar's CSRF cookie on the following request.

Origin/Referer must match the current configured site and Host; a different configured public site is not a CSRF authorization. Cross-site Fetch Metadata is rejected. CLI requests may omit source headers but must still supply both double-submit values and the custom header. Forwarded host/proto headers never choose cookie security. Before setup, a browser Origin (or Referer) with exactly the request Host authority selects HTTP loopback or HTTPS, including HTTPS localhost/IPv4/IPv6 loopback. Scheme selection does not authorize a source: Forge still validates Origin (preferred over Referer) and Fetch Metadata against that origin. With no matching browser source, CLI bootstrap defaults to HTTP loopback or HTTPS domains; an HTTPS loopback CLI must supply its same-host Origin or Referer. The panel explicitly uses same-origin Referer policy for CSRF bootstrap even when the document suppresses referrers. After setup, only registered site authorities select cookie policy. Initial setup, anonymous login/registration, email challenge consumption, logout and management mutations all use this boundary. OAuth refresh/token endpoints remain unimplemented under their own capability issue; future cookie-authenticated refresh writes must inherit this policy rather than introducing an exception.

## CORS

CORS is disabled by default. Public sites, redirect URIs and arbitrary request hosts never create an allowlist. Deployment configuration can enable a bounded exact origin list; wildcard, opaque and invalid origins fail configuration validation. The runtime adapter resolves an atomically replaceable validated snapshot on every request, so an existing router sees a replaced policy immediately. The shipped configuration is loaded at startup; there is no new management API or file watcher for CORS. An embedder can call HttpSecurity::replace_cors with validated deployment configuration.

Cross-origin Cookie login is unsupported: allow_credentials is always false and no Access-Control-Allow-Credentials header is emitted. Explicit allowlisted public reads/preflight may work without credentials, while credential-bearing unsafe actions must independently satisfy same-origin CSRF. CORS admission never authorizes CSRF. Responses vary on the CORS request headers; preflight passes HTTP and auth admission quotas before the adapter can return 204.

## Peers and quotas

The TCP server supplies ConnectInfo<SocketAddr> to the router. Trusted proxies are an explicit list of IPs/CIDRs, rejected on malformed input. Forge ignores forwarding headers from an untrusted direct peer, walks a trusted chain according to its shared policy, and supports IPv4/IPv6. When transport peer information is missing, the global IP governor uses a shared localhost bucket and the authentication keyed governor uses an explicit unknown-peer key; neither derives a peer from headers. UDS/alternate transports must provide a trusted extension/adapter or size/disable the process-local IP policy appropriately.

The general IP quota applies to /api/v1 requests. Auth paths and setup additionally have a separate IP-keyed authentication quota, checked first; a rejected authentication check does not debit the general quota. Both use Forge shared normalized keyed governors with Forge client-IP resolution; canonical IP keys allow admission decisions before CORS without executing a handler. Gate does not implement a governor. Malformed/forbidden requests and preflight consume admission tokens before their handler outcome is known. Router clones and routers reconstructed from the same AppState share buckets. Defaults are 300 general tokens replenished one per second and 100 authentication tokens replenished one per two seconds. Configuration values are nonzero typed inputs, and burst windows exceeding the governor's supported nanosecond range are rejected before construction. Periodic request maintenance removes expired governor entries. Health/static routes are exempt; these quotas are per process, so multi-replica deployments also need ingress-level admission if a globally shared HTTP limit is required.

Database-backed identifier/action Account security budgets continue to provide durable brute-force protection and survive router recreation/restarts. Governors only supplement those budgets. HTTP rejections use Gate's rate_limited error envelope with retryable metadata and Retry-After rounded up from Forge's actual wait; durable Account cooldowns retain their existing policy.

## Layer order and responses

From outside to inside: optional instance metrics extension/middleware, compression, request correlation, Forge security headers, API no-store/no-cache/no-referrer policy, admission decision, runtime CORS, admission enforcement, route-specific Account/CSRF and readiness checks, handlers. Admission debits applicable quotas once and carries a typed Forge rejection in request extensions. Actual 429s pass through CORS, retaining exact allow-origin, exposed Retry-After and Vary headers for allowlisted callers. If CORS short-circuits preflight or denial, the outer decision applies 429 while retaining only CORS response headers. Rejected requests never reach product handlers; denied origins never receive allow-origin headers. The outer response policy covers early CORS/CSRF/429 errors; Forge preserves stricter Referrer-Policy and product CSP. Gate injects its typed auth.forbidden envelope through Forge’s explicit rejection_response callback; request parsing failures and response construction failures retain separate mappings. Downstream empty 403 responses pass through unchanged. Health and protocol responses retain their own transport contracts; OAuth/OIDC protocol endpoints must not be wrapped in management envelopes.

Product HTTP adapters live in src/api/middleware/{state,cors,rate_limit,account,response_headers}.rs; api/mod.rs shows actual layer order. Input/authentication extractors live in api/extractors.rs, Cookie policy/building in api/cookies.rs, and AccountError mapping in api/response.rs. Router groups distinguish public bootstrap reads, CSRF-protected setup writes, and ready-required Account/auth/management routes. Readiness and CSRF are independent; health and future protocol routes retain their own boundary.

Cross-module route groups and their policies are assembled in api/routes/mod.rs; account routes only register Account/auth handlers. Drive likewise owns JSON transport policy in api/extractors.rs and Cookie construction in api/routes/auth/cookies.rs. Gate keeps cookies at the API boundary because setup, Account handlers and CSRF middleware all consume the same host policy; Axum authentication uses an extractor where Drive uses Actix authentication middleware.

Validation lives in tests/accounts/http_middleware.rs, the existing Account lifecycle/transaction tests, frontend CSRF unit tests, and real browser account flows. Metrics/request-ID integration is additionally tested through the real assembled router. The integration must be checked with the Axum-only dependency feature tree and the documented project test commands before capability status is advanced.
